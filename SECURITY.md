# Security and release scope

AppSEND (Android 1.6 / Windows 1.6) uses fresh committed ECDH keys, encrypts metadata and data after the public handshake, and authenticates streamed records with AES-256-GCM plus an ordered final SHA-256 check. Sending is authorized by the local Send action or gesture; incoming files are automatically accepted by default at the user's request. The optional automatic-receive preference restores manual approval when disabled. A remote request to fetch a staged item requires the owner's approval. Read the protocol before changing either implementation.

At the user's request, version 1.2 removes the six-digit comparison from the interface. The wire implementation retains the SAS calculation for compatibility, but it is not presented as authentication. Device labels and the first key agreement are unauthenticated: an active LAN attacker can impersonate a peer or interpose its own encrypted sessions. Content encryption and integrity protect an established session, not the identity of the endpoint. Automatic receiving allows any device that reaches the LAN listener to write a declared transfer into the receive folder. It can consume disk space without a prompt; stop availability or disable automatic receiving when unwanted. Files and links are never executed or opened automatically. Use a trusted LAN; do not describe this version as providing authenticated peer identity.

Grab mode requests optional front-camera access only on its foreground capture screen. Frames are analyzed in memory on the phone and are neither saved nor sent. A positive fist capture followed by an open palm authorizes sending the staged file to the frozen selected PC. A peripheral hand exit is an alternative. An open palm without capture never authorizes sending. Cancel, leaving the screen, camera errors and timeout reset the grip. This is a gesture command, not a biometric identity check or spatial monitor detection.

No external server receives transfer content. Runtime dependencies are local. Discovery labels, IP addresses and traffic characteristics remain visible on the LAN. The HTTP capability header is visible but one-use, and authenticated encryption is still required to upload valid data. A LAN attacker can interrupt, jam or exhaust network connections. This is not an anonymity system or a defense against a compromised endpoint.

The desktop renderer is sandboxed with context isolation and Node integration disabled. CSP forbids remote content and renderer networking. A small preload bridge routes actions to the main process. IPC accepts only known local renderer webContents. Received names and text are rendered through text APIs. Web windows cannot open external pages or navigate to arbitrary content.

Received files are untrusted content. AppSEND writes them to the receive folder with sanitized names and random prefixes. It never executes files, automatically opens links or changes the system clipboard. Android exposes files only through a non-exported FileProvider and temporary read grants after an explicit user action.

File streams use bounded chunks. An accepted file can consume its declared size on disk; consent is not a disk quota reservation. A disk-full error fails the transfer and removes the partial file. Crashing or losing power may leave an owned `.part` file; it is not presented as received content and may be deleted manually after restarting. Unknown-length Android provider streams require additional staging disk space. Interrupted transfers restart from zero.

Sessions are limited to eight per engine; the Windows HTTP listener also caps concurrent connections. These bounds reduce accidental overload but do not provide comprehensive hostile-network rate limiting. Restrict Windows access to Private/LocalSubnet networks and stop Android availability when unused. Do not forward the listener through a router or expose it publicly.

Before a public production release, perform an independent review of the custom handshake and state machine, fuzz both network parsers, run dependency and signing checks, qualify the device/network matrix, measure frame/timing performance, and define support and update policies. The local development APK and unsigned Windows installer do not establish publisher identity.

No signing material, external credentials or fixed runtime encryption key is embedded. `protocol/golden.json` contains a public test-only private key solely for interoperability validation.
